## 1. The five fold lines against the code

1. **The task runs the whole after-write on every gated write: holds.** `owned_write` calls `after(&out, cause)`
   when the write's future is Ready, with no condition on the request (`owned_write.rs:168-189`). It then drives
   that future inside the same `wait_until` task (`:191-195`). The task ends only when the after-write is done and
   no cover is in flight (`:196`). `routes.rs:2072-2087` makes `after` call `finish_past_deadline` (`:771`). That
   function runs these steps, in order:
   - the outlived counter under `RequestGone` (`:795-797`);
   - the line, and the walk count, which is counted by the task under past-deadline and request-gone only (`:798-810`);
   - `guard_landed` (`:811-814`);
   - the #513 write-side guard (`:826-893`);
   - S2 (`:894-934`);
   - the notes (`:935-940`).

   Every path reaches it:
   - **The write errs.** It takes the `Err` arm at `:817`. The guard still runs, and there is no S2, as in the
     request.
   - **The write is not durable.** S2 enqueues through `past_deadline_ack` (`:909`).
   - **The request is still waiting.** The cause is `InRequest` (`owned_write.rs:176`). The task runs its own copy
     and the request runs its copy beside it.
   - **The request is gone.** The cause is `RequestGone` (`:173-174`).
   - **The request passed its deadline.** `handle.past_deadline()` (`routes.rs:2100`) runs synchronously after
     `within_deadline` answers `Past` (`ef_deferred.rs:151-175`). That function polls the work first, so a write that
     had already ended is `Done` and never mislabelled.
   - **`OVERLAY_DB` is missing.** The task logs and returns (`routes.rs:789-794`). The request's path then has no
     D1 either. This is unchanged.
2. **The cover starts from `AbortSignal`, never from `Drop`: holds.** `Handle` has no `Drop` (`owned_write.rs:40-62`).
   `gone` is `RequestSignal::gone()`, and the cover is started once from inside the task's poll (`:155-167`). See
   question 2.
3. **No hand-over wait: holds.** The output is put in the slot, and a waiting request's waker is woken
   (`owned_write.rs:180-183`). Nothing reads the request's state. A task whose request is never polled again ends
   (`fix936_g`, `resumed=false`, asserts `ended.is_ready()`). LOW-1 of the lens is gone.
4. **The never-dropped pin: holds.** See question 4.
5. **One cause word on every line, and L53's measure on the task's line: holds.** Every `console_log!` in
   `finish_past_deadline` carries `{word}` or `{cover}` (`:791`, `:801`, `:821`, `:832`, `:857`, `:877`, `:890`,
   `:904`, `:921`, `:930`). `fix936_h` pins this. READ-936 section 5 now reads the task's own line, with all three

## 2. Shape (a): the signal, the flag, the handler

**What Cloudflare documents.** The compatibility flags page
(`https://developers.cloudflare.com/workers/configuration/compatibility-flags/`, read 2026-10-27) gives the entry
"Enable `Request.signal` for incoming requests" only two rows: "Flag to enable `enable_request_signal`" and "Flag to
disable `disable_request_signal`". It has no "Default as of" row. The same page says: "When you use the
`enable_request_signal` compatibility flag, you can attach an event listener to Request objects, using the signal
property. This allows you to perform tasks when the request to your Worker is canceled by the client." The Request
page (`/workers/runtime-apis/request/`) adds: "This allows you to perform cleanup tasks or write to logs before your
Worker's invocation ends." So `compatibility_date = "2024-12-01"` does not turn it on; the flag must be named.

**Where the flag is.** It is named at `wrangler.toml:5`, at `wrangler.low.toml:18` (top level, the prod render
`low-overlay`) and at `:239` (`[env.beta]`). `fix936_i` pins all three. The beta line is redundant, because
`compatibility_flags` is an inheritable key, but it is harmless.

**Without the flag.** `RequestSignal::of` reads `signal` with `Reflect::get`. If the value is not an object, or not
an `AbortSignal`, the result is `None` (`owned_write.rs:80-88`). `gone()` is then `pending()` for ever (`:110-111`).
The task does not wait on `gone`: it ends when the after-write ends. If a signal is present but never fires (a
runtime with no flag that still serves an inert signal), the outcome is the same. The `onabort` handler is a JS
`resolve`, so dropping the `JsFuture` leaves no Rust closure behind.

In every one of these cases there is never a throw and never a hang. Two things are lost. First, there is no cover:
B4 is as it was on `8cf04f54`, a platform cut with no job. Second, the cause read is `in-request`, so no
`request-gone` line is printed and the counter stays 0. READ-936 section 5 states this.

**The abort handler survives the cancelled request: holds.** The listener only resolves a promise
(`owned_write.rs:103-105`). The work runs in the task, and the task runs under `ctx.wait_until` (`routes.rs:2089`):
- the `JsFuture` wakes the task;
- the task polls `gone`, and on Ready it boxes the cover (`defer_request_gone`) and polls it beside the write
  (`owned_write.rs:155-167`);
- the task does not end while the cover is in flight (`:196`).

So the put lives as long as `wait_until` does, which is until the platform's cut about 30 s after the cancel. It
never depends on the cancelled invocation. A signal that is already aborted when the arm reaches `gone()` is Ready
at once (`:100-101`).

**The bytes at rest are the whole submission.** `defer_request_gone` (`ef_deferred.rs:710-735`) calls `put_at_rest`
with `tagged`, which is the whole BEEF and its topics, and with `PAST_DEADLINE_JOB_DELAY_SECS`. The reference is
`job_reference(topics, beef, off_chain)` (`:794`), a content key. An open job of the same reference returns early
(`:796-799`). So a past-deadline put and an abort put of one submission are one job. Two that race may send two
delayed messages, and each one's run is the arm again, so the replay is idempotent.

The run replays the write whole while the coin is unspent. In a half write the applied row is the write's last
statement, so the dedup check does not fire. The admission runs again over `INSERT OR IGNORE` outputs and writes
the lookup services' rows.

## 3. Two copies of the after-write

The two copies coexist only under `InRequest` (the request was still waiting at the write's end). Under
`PastDeadline` the request returns its 202 and runs no after-write (`routes.rs:2094-2117`). Under `RequestGone` the
request is either never polled again (s1) or resumed with its I/O not running (s2, the READ's evidence).

Each statement is idempotent under the real schema:
- **`open_eviction`** is a read.
- **`evict_txid_everywhere`** is one atomic batch (`eviction_write::evict`, fenced by `READMISSION_FENCE_SQL`). The
  second copy finds nothing to move (`moved` 0), and the ledger row is unchanged.
- **`readmit_if_evicted`** reads `readmittedAt IS NULL` first (`admit_fast.rs:1491-1508`), so the second copy is a
  no-op.
- **`guard_landed`** moves and reads as the subject's guard does.
- **The notes flush** takes the isolate's pending notes, so the second flush finds the rest or nothing.
- **S2** sends two messages only when the write is not durable. The consumer's dedup (one applied row) makes the
  second a dupe. Past the inline room, both name one R2 object, and door 3's twin rule covers it: the first ack
  deletes the object, and the second finds the applied rows (`queue::judge_missing`).

**The counter is bumped once per write.** `submit_write_outlived_request_total` is bumped only at `routes.rs:796`,
under `RequestGone`, by the task. The task runs `after` exactly once (`after.take()`, `owned_write.rs:178`). The
request never bumps it (grep: `ops.rs:58` names it, and only `routes.rs:796` and the `fix936_h` text use it). L53's
measure does not double-count.

The other counters shared by both copies are gated by `counts` (`:788`): reevicted, ledger-unreadable, mutation
fault, queued, refused, readmitted-by-fresh-accept and the walk count. Under `InRequest` the task does not count
them, and the request counts them once. See LOW-1 for the window this leaves.

**What the extra copy costs per gated in-request write.** One `open_eviction` read. One refused-memo read when the
door's readmission faulted. One notes flush, usually empty. One more log line. On a write that is not durable, a
second S2 enqueue. A cancel during the write adds #838's put (one row, a D1 or R2 put, one delayed send) and one
counter write.

**Ceilings: none moves.** `tools/lane-499/ceilings.json` has no cell that drives the gated arm. Its #838 row (`:672`)
says the gated arm is "not driven by this tier" (Arcade, and mainnet in its background). `submit-admit-1` (`:142`) is
an operator `historical-tx-no-spv` submit, which takes the `_ =>` arm at `routes.rs:2121` and never the owned task.
The added cost is therefore not measured by any ceiling (LOW-3).

## Findings

**LOW-1: a cancel between the write's end and the answer loses that write's counters.** File: `routes.rs:788`,
`owned_write.rs:171-177`. Under `InRequest`, `counts` is false, so the task counts nothing and leaves the counting
to the request. If the client goes away after the write ended but before the request's post-answer counter flush,
the reevicted, queued, mutation-fault and ledger-unreadable counts for that write are lost. The outlived counter is
not bumped either, as designed. The guard and S2 still run in the task, so this is telemetry only. To fold it: let
the task count when its own signal fired before the after-write ended, or have the request count from the task's
report. This is not required to land.

**LOW-2: two concurrent copies of the guard widen the stale-readmission race, in the door-readmit-failed arm only.**
File: `routes.rs:828-862` and `:2169-2209`. If a fresh corroborated refusal writes its refused memo between the two
copies' memo reads, one copy readmits and the other evicts, and the order decides the outcome. The base had the same
race with one copy, against the refusal pass itself. It is rare (the door's readmission must have faulted first),
and the network's MINED word and the conflict pass correct it. State it and move on.

**LOW-3: no ceiling measures the gated write's after-write.** File: `tools/lane-499/ceilings.json:672`. The added
cost of every gated write is not in any ceiling, and the cell measures no rows. The #838 row's sentence "not driven
by this tier ... the tier's loopback seal refuses" is now stale, because the #936 cell drives the gated arm under
the seal. To fold it: let the cell record its rows read and written per leg, and amend the row's sentence.

**LOW-4: nothing executes the signal path before the land.** File: `owned_write.rs:79-112` (wasm32 only),
`request_gone_route_ci.mjs:33-36`. The cell is the only executor of `RequestSignal`, it has not been run, its proxy
question is open, and it does not run the job. Its egress guard reads the tap at the end of the tier, after any
leaked request. The beta window under the flag is the only test of the platform's disconnect. The bytes involved are
an unspendable JOIN.

**NOTE-1.** `fix936_c` is a model of the base's class, not a pin of the fix.

**NOTE-2.** The changed `#838` log text is quoted only in history documents.

**NOTE-3.** The prod render carries the flag. It is enabled at promotion, and only this arm reads the signal.

**NOTE-4.** The flag line under `[env.beta]` is redundant (an inheritable key), and `fix936_i` requires it.
