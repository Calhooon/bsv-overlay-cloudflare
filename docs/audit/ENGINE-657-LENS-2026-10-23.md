## Verdict: SOUND (nothing above LOW)

The rule is right for what it fixes: on this tip the same bytes meet the same
engine store and answer the same word on every presentation, a transient hook
fault heals on the replay whole, and the moved pins keep every head property
they protected. Five LOW findings and six notes below, none a wrong press, a
doubled row, a victim's transaction held by a stranger, or an honest body held
out. Option (b) is NOT needed on this tip: no production hook can be made to
fault deterministically by a crafted body (the six PushDrop hooks' `Err` arm
parses the topic manager's own bytes, `ls_pot`'s faults are D1's alone), so
the permanent arm of the rule is reached only by a code bug or a D1 refusal,
and its repair is the shipped dead-letter lever after the hook is fixed.

## Findings

### LOW-1. Under Rule 6 the deterministic arm is the PERMANENT mode for LOW's pot, where the old mode was a self-healing partial index; stated by the lane, not weighed

`crates/overlay-engine/src/engine.rs:1852` (`spend_notify_faulted`) and
`:1971` (`insert_faulted || admit_notify_faulted`). The brief's test:
`~/bsv/epoch/NETWORK-ENFORCEMENT-RULES.md` Rule 6, "do not trade a
self-healing failure for a permanent one".

The input: an honest JOIN whose admission trips a hook that faults every time
(a bug in one of the sixteen hooks for a shape the fleet never produced, or a
D1 refusal of one of its rows).

Before the PR, for LOW's pot: `tm_pot` admits the covenant on shape and needs
no previous coin, so the engine held the pot's output, the faulting lookup
service's rows were missing, every OTHER lookup service's rows stood, the
settle's later submit found the coin and `ls_pot`'s spend hook recorded the
spend and the verdict, and the replay (judged with no coin, which for a JOIN
under `tm_pot` is the same judgement) re-told the hooks each time, faulted
again, and parked a `fault` letter. The index was partial by one service and
the engine complete.

After the PR: nothing of the pot is held in `tm_pot` for good (three replays,
one `fault` letter, `e657_lens_a`), so EVERY engine-driven write for that pot
is lost while the hook is broken: the settle's `output_spent` to `ls_pot`
(the pot's `spent`, `spendingTxid`, the #284 verdict, the #406 signers), the
`hop_pot_links` the spend feeds, the board win. The hop side is unaffected
(`tm_lowfund` admits nothing of a JOIN, so that topic has no insert and no
admit hook, and lands independently). The janitor's missing-spend pass heals
`spent` from the couriers within its hour; the verdict and the board win are
not healed until the hook is fixed and the letter re-driven.

The felt and owed list (brief 2a): the door still answers 200 with
`X-Overlay-Mutation: queued` (`routes.rs:2239`, S2: a report that is not
durable enqueues and acks), the STEAK still names the pot (`error_paths`,
`steak["Hello"].outputs_to_admit == [0]`), so the client's `steakAdmission`
(`bsv-low app/src/lib/overlay.ts:2688`, it reads `outputsToAdmit` and
`coinsRemoved` only, never the header) reads `admitted`; `/utxo-status` reads
`pot_records` (`low-app-layer routes.rs:289`), so the pot reads present iff
`ls_pot` was told before the fault (LOW-2: the map's order); the owed list
serves its refund row gated by the network latch or the proof (FIX-831,
`fundingHeld`), which the pending watch still writes for the subject. The
tower's co-sign path needs the BEEF, not the index (`low-tower-key`: the
derived key signs the covenant digest over the bytes); money is on chain
either way.

Which this is: the deterministic arm is permanent (until a code fix and
`POST /internal/redrive-dead-letters`), the old arm was self-healing-partial
for LOW's shape and WRONG for a head chain (Zanaadu's registry: the coin-less
replay admitted output 0 alone, the case the PR answers). Both arms need the
hook fixed; the PR trades a partial index with a complete engine for a clean
hold-out with a shipped lever. Accepted as the lane states it, because no
honest body reaches the arm today (the hooks audit below) and the repair is
one lever, where the old arm's partial rows needed a bespoke backfill. The
fix shape if it ever bites: option (b) (the applied row recorded, a durable
"notify owed" row settled by the replay), which keeps the engine's word right
during a deterministic fault; the lane's objection to it ("applied" beside an
owed row for ever) describes exactly the pre-PR LOW state, which was the more
benign one for LOW's shapes.

### LOW-2. "The same bytes, the same word" holds for the ENGINE store; the lookup stores vary with the HashMap's order, and a healthy hook is told N+1 times

`engine.rs:65` (`lookup_services: HashMap<String, Box<dyn LookupService>>`),
`:1923` (`for ls in self.lookup_services.values()`), `:1943` (`break` at the
first hook that faults). Case `e657_lens_1` (built here): two services,
`ls_a` healthy and `ls_b` faulting deterministically on head 1's output 0;
over twelve presentations the engine's store was put back identically every
time, and `ls_a` was told of output 0 in 7 of the 12 (per presentation:
`[1, 1, 0, 0, 1, 1, 1, 0, 1, 0, 0, 1]`); the replay then told `ls_a` of both
outputs, so `ls_a` held 8 tells of one output the engine holds once.
Consequence: which lookup services hold rows for a held-out transaction is
not a function of the bytes; `/utxo-status` can answer present on one
presentation's state and absent on another's for the same pot (LOW-1's
`pot_records` row). Money: none (display). The CLAUDE.md sentence "the store
byte-equal after the first" should name the engine's store. The lane's
"hooks must be idempotent" is load-bearing and verified for every production
write (the hooks audit); Zanaadu's registry hook emits one queue event per
tell (`overlay-lib/src/user_registry/lookup_service.rs`, `emit_admitted`), so
its consumer must dedup by txid (theirs; stated).

### LOW-3. Rows keyed on an outpoint the engine does not hold (brief 2b)

The hooks told before the fault keep their rows with no coin behind them and
nothing retracts them (D17 rule 5, as the lane states). Which production hook
writes such rows and who reads them: `ls_pot` (`pot_records` and `pot_beefs`:
`/utxo-status`, `/pots-view`, the owed list's hydration and `fundingHeld`,
the retire and conflict passes, the leaderboard's derivation triggers);
`ls_hopparty`, `ls_potparty`, `ls_potrefund`, `ls_collected`, `ls_result`,
`ls_hand`, `ls_proof`, `ls_reveal` (markers: the owed list, the lobby, the
board's hands); `ls_low` (`low_records`: the lobby). Before the PR the coin
existed behind every such row and only the applied row was withheld; after,
the coin is gone and the rows stand. Worse in one shape: a `pot_records` row
with `spent = 0` whose pot the engine never holds is never marked spent by
the settle's submit (no coin found, no `output_spent`), so until the janitor's
missing-spend pass (hourly, courier-fed) the owed list can offer a refund for
a settled pot, which the network refuses `UTXO_SPENT` (the loop 44 class of
FIX-837). Before the PR the settle's own submit marked it. Display only, the
network judges the press, and the window needs a hook faulting every time.
Same or better in every other shape: a marker row for a held-out marker is
what the reference leaves too.

### LOW-4. Two faults in one submit: the undone output stays LISTED

`engine.rs:2684` (`undo_inserts`: a delete that faults leaves the row,

is #559's limit (1) exactly, with a new road into it; converges by the
successor or the replay; stated, not changed.

### LOW-5. The GASP cursor and the yieldless bound under a hook that faults every time

`gasp_overlay.rs` finalize submits (`submit_finalized_graphs` stops at the
first that does not land). Before the PR a hook fault in a finalize submit
landed the store (applied row withheld, outputs held), so the next tick's
walk saw the outputs held and did not re-submit. Now the outputs are not held,
the UTXO fails, the cursor stays below it, and every tick re-fetches and
re-submits that graph (the lane states "the cursor held under GASP"). Not
stated: with a per-graph budget (the worker's) such a sync is YIELDLESS
(graphs attempted, nothing finalized), so after 12 syncs and 3 h D16 counts
the peer failed and quarantines an HONEST peer for our own hook bug, re-probed
every 6 h and failed again. Reach on LOW: the GASP topics are SHIP, SLAP and
UHRP, whose hooks' only fault surface is D1 (the PushDrop `Err` arm is
unreachable, below). PLAUSIBLE by reading, not run against a test peer.

## The hooks audit (every production hook in this tree, and Zanaadu's)

Admit hook fault surfaces and the production write's shape under a re-tell:

- `ls_pot` (`pot/lookup_service.rs:168`, `:301`): no `Err` but storage; a
  parse failure, an index out of range or a shape mismatch is `Ok` and a
  no-op. D1 `store_record_sql()` is insert-if-absent with stored-wins fill,
  its SET never touching `spent`, `spendingTxid` or `spentConfirmed`;
  `POT_BEEF_ADMIT_WRITE_SQL` is guarded by `beef_write_allowed` (never
  shorter, never over a verified row); `mark_spent` is UPDATE-only. Pinned
  here on the memory store (`e657_lens_ls_pot_hooks_are_idempotent_under_a_retell`)
  and on real SQLite over the shipped statements
  (`e657_lens_pot_record_retell_under_real_sqlite_keeps_one_row_and_the_spend`:
  two tells one row, the spend pointer kept through a third tell).
- `ls_low`, `ls_ship`, `ls_slap`, `ls_uhrp`, `ls_agent`, `ls_dm_delegation`:
  `Err` on `Script::from_binary` or `PushDrop::decode` of the admitted
  locking script. Unreachable by a crafted body: the engine hands the topic
  manager its ONE parsed `tx` (`engine.rs:3503`), the manager admits only an
  output whose `locking_script` PushDrop-decodes, and the hook decodes the
  same output's bytes written back (`to_binary` then `from_binary`). Writes:
  `low_records` and `reveal_records` `INSERT OR REPLACE` by key; SHIP, SLAP,
  UHRP, agent and delegation records keyed by outpoint, their spend hooks
  deletes by key.
- `ls_hopparty`, `ls_potparty`, `ls_potrefund`, `ls_collected`, `ls_result`,
  `ls_hand`, `ls_proof`, `ls_reveal`: `Err` only on a payload mode the engine
  never sends (the engine builds the payload from `admission_mode()`); an
  unparseable marker is `Ok` and a no-op; D1 writes `INSERT OR IGNORE` on the
  outpoint primary key (`d1_discovery.rs:3814`, `:4122`, `:4557`, `:7147`,
  `:5773`, `:6246`, `:6490`); spend hooks are no-ops (permanent facts).
- Zanaadu (`~/bsv/zanaadu/overlay-lib/src/*/lookup_service.rs`): the registry
  hook's `parse_admitted(payload)?` is the deterministic `Err` of #414 (their
  fix: never an error on a foreign output); `upsert_chain` is idempotent;
  `emit_admitted` is one queue event per tell (LOW-2).

The first fault in a hook stops the inserts at that output (`:1943`), so an
LS later in the map's order is told nothing of the transaction; the spend
hooks of the previous coins ran for every LS before any insert (`:1836`).
