## 1. The rule

**Holds.** "Open" is a `pot_evictions` row for the txid with `readmittedAt IS NULL`. In Rust that is
`EvictionLedgerEntry::readmitted_at == None`, read by `evictions_by_txid_sql` (`storage.rs:417-424`, `SELECT
lower(txid), evictedAt, readmittedAt, reason ... WHERE txid IN (...)`). In SQL it is the conjunct above, and in the
judge `OPEN_EVICTED_POTS_SQL`. It is the same predicate as the door's `admit_fast::OPEN_EVICTION_SQL`
(`crates/overlay-cloudflare/src/admit_fast.rs:807`).

The join key is the pot's own txid. The ledger's txid is lowercased by every writer
(`evict_txid_everywhere_repointed`, `admit_fast.rs:1296`; `readmit_if_evicted`, `:1481`). `ls_pot` lowercases its
keys (`lookup_service.rs:531-534`) and its lookup (`:590`). `/pots-view` compares `ev.txid = p.txid`, where `p.txid`
already matched the lowercased bind (`Outpoint::db_txid`).

Every producer named reads the same. The conflict pass (#602), Arcade's terminal word (#519), the ghost retire
(#831) and the write-side guard (#513) all reach the ledger through `evict_txid_everywhere[_repointed]`, which writes
`OPEN_EVICTION_MARKER_SQL` (`admit_fast.rs:785`) first, in its own statement (`eviction_write.rs:294-303`). Grepping
`crates/*/src` finds no other writer that inserts an open row, apart from the ledger fence `READMISSION_FENCE_SQL`
(`eviction_write.rs:25`), whose row is closed, and the re-opens covered under LOW-1.

A marker on a DIFFERENT txid never hides a pot. A marker on a JOIN hides only the `pot_records` rows keyed by that
JOIN's txid, which are its own covenant outputs. Hop rows are keyed by the hop's own txid and are not hidden by
their spender's marker (but see LOW-2). A readmitted row is held at the next read (`fix937_b`, both crates). No
isolate memo stands between the ledger and these reads: `ls_pot` and `/utxo-status` read it on each request.

## 3. The owed judge

## 5. The write race

Between the deferred landing and the guard's move, the row is under an open marker, so every closed site now serves
the twin. After the guard's move the twin is the row. Readmission:

1. `readmit_if_evicted` (`admit_fast.rs:1480`) restores the twins;
2. it re-marks the spends;
3. only then does it stamp `readmittedAt` (`:1540-1549`).

Between steps 1 and 3 the restored row is hidden (the fail-safe direction, milliseconds). After step 3 it is held
at the next read. There is no window that serves held between the marker and the readmission, except where the
ledger read itself faults: `ls_pot` and `/utxo-status` then serve the row as stored, as before (stated in the PR,
NOTE-2).

The judge's read is NOT best-effort: `read(...).await?` fails the subject's hydrate, so the previous judgement stands
and the dirty mark keeps it pending.

There is no isolate memo of a pot's held state on these paths. The residuals are LOW-1 and LOW-2.

## Findings

**LOW-1: a readmission whose stamp faults is now served evicted.** `readmit_if_evicted` restores the twins and only
then stamps (`admit_fast.rs:1512`, `:1540`). When the stamp's UPDATE faults (`:1545-1549`, counted
`COUNTER_ADMIT_FAST_READMIT_INCOMPLETE`, logged "the rows are back"), the restored rows sit under an open marker.

The same holds where a yield or the belt re-opens a row whose restore faulted (`:1360-1375`, `:1605-1616`). Those
re-open only while the twins still hold rows, so hiding there agrees with a half-done move.

The failing input is a MINED proof push for an evicted JOIN whose `READMIT_EVICTION_SQL` faults once:

- before, `ls_pot` and `/utxo-status` served it `known:true` and the judge kept its press;
- now it is `known:false` with the old word (the felt's `evicted` verdict and `FUNDING_BLOCKED`), and the press is
  dropped;
- this lasts until the next door accept, MINED push or `/admin/readmit` closes it.

No sweep retries the stamp. It is fault-only and counted, and it agrees with the ledger's own contract ("the row
stays open"; the door already refuses re-presents under it). The client had already latched the block at the
eviction proper (B1).

Fold: one sentence in the PR body and the register. Optionally, a follow-up issue for a scheduled re-stamp of an
open marker whose twins are empty and whose `pot_records` rows are present. No code here.

**LOW-2: a JOIN under an open marker still holds its hops' spend pointers at the read.** The late landing runs
`ls_pot`'s `output_spent` (`lookup_service.rs:301`, `mark_spent` at `:425-436`) with no ledger check. The seat's hop
rows read `spent:true, spendingTxid=<the refused JOIN>` on `ls_pot` and `/utxo-status`, and the judge reads the hop
as taken by a pot it now drops. That means no sweep press until the guard's move releases the spends.

This is pre-existing and not widened by this PR (B3). It is a liveness window for the seat's own hop and never an
honest party's sats. It is closed at the write by PR 183 (the landing completes the eviction) and by the guard.
Honouring the spender's marker at the read would mean reading the ledger for spender txids, and serving an
"unspent" for a hop the JOIN may yet have spent; it is not recommended.

Fold: state it in the PR body.
