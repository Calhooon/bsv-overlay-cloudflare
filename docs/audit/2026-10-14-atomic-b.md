## Hooks and report

```rust
fn check_admitted(&self, payload: &OutputAdmittedByTopic) -> Result<(), LookupServiceError>;
fn check_spent(&self, payload: &OutputSpent) -> Result<(), LookupServiceError>;
```

Both default to `Ok(())`. The trait contract at `lookup_service.rs:57-80` requires
pure validation: no writes, no I/O, no externally observable side effects. A
service shares its topic guard and parser with its corresponding notification
hook. The signatures are synchronous. Test spies record calls only to observe
this contract's invocation boundary.

`MutationReport::refused: Vec<AdmissionRefusal>` carries each check refusal's
`topic`, registered `service` key, `site: &'static str`, and original typed
`LookupServiceError`. Sites are `lookup_service.check_admitted` and
`lookup_service.check_spent`. Errors now implement `Clone`, `PartialEq`, and `Eq`
so reports retain those traits. Refusals are sorted by topic, service, site for a
stable word across service-map iteration orders. They are separate from mutation
faults. `is_durable()` is false if either collection is nonempty. A door reads
these fields, never an error-text prefix. Existing non-refusal summary strings
and `Engine::submit` STEAKs are unchanged.

## Exact apply boundary

`crates/overlay-engine/src/engine.rs:1735` starts preflight in
`submit_counted_inner`. The calls are `check_spent` at line 1756 and
`check_admitted` at line 1770. They follow `run_validation`, the complete
`successors_waiting` call, and the carried predecessor's real re-judgement. They
precede the Phase 3 loop at line 1788, which began at line 1614 on 0.1.0. The first
possible apply write is `mark_utxo_as_spent` at line 1878; with no previous coin,
it is the later `insert_output`.

Each eligible (topic, spent coin, service) and (topic, admitted output, service)
is checked once, including `SpendNotificationMode::None`. Checks continue over
all payloads even after a refusal. Failed, deduped, read-faulted and waiting topics
are skipped. A refused topic is held unapplied, with no apply writes and no
notification hooks. Other topics can apply. `submit_validate_only` never enters
this function, so a dry run never checks or applies; the following real submit
checks normally.

`LookupPayloads` builds both check and notification payloads from the same
transaction, subject-named Atomic BEEF, topic, index and off-chain values. It
holds one payload at a time, including WholeTx, with no collection of cloned BEEF
bodies across checks. All two admission modes by four spend modes are exercised.

B is topic-local. The whole-store byte-equality witnesses submit only the
registry topic; they retain the spike's old coin, outputs 0 and 2, refusal on 2,
and TYPE 2 / TYPE 1 manager branches. A separate two-topic witness proves the
refused registry remains untouched while proof admission lands. This does not
claim submit-wide rollback when an accepted sibling, a manager judgement or a
carried predecessor writes.

## What B does not cover (design section 4, verbatim)

**What it does not cover.** Every fault that is not a parse: a lookup service's D1 write failing after
the engine's writes landed, a queue or R2 error inside a hook, a read the hook needs, an isolate killed
mid-apply, a CPU or wall limit between two writes. Those still leave a partial admission, and the replay
can still take a different path (L1, L2 hold only for deterministic refusals).
