## 3. Question 2: does `carry_shed_rows` carry a row the cut pass would have CHANGED, and can a carried row be pressed?

`budget_cut` is the walk's CLOCK, set when `over_budget()` trips in the probe phase (`routes.rs:4297`), the spender reads (`:4904`), the courier reads (`:5018`) or the pay-vout pass (`:5464`). So on a `budget_cut` pass every game the cursor hydrated IS derived, with fewer probes and spender reads (words withheld); a row the pass did not derive is one the pass judged NO ROW on the inputs it had, or one it could not hydrate.

**Yes, the carry can carry a row the uncut pass would have changed**: a hop since spent into its pot (the uncut pass retires it, the cut pass carries the old `sweep-hop` row as shed), a game collected this hour but not yet verified (`collected_verified` is the only exclusion, `owed.rs:1806`). Each is carried with `claimable: false`, the old word moved to `claimableBeforeShed`, `refresh: "shed"`, `stale: true`, `carried: true`, `retryAfterMs` 30 s, its first `judgedAtMs` kept and the keep window one hour from that first judgement (`OWED_WITHHELD_KEEP_MAX_MS`, `owed.rs:1474`), so a cut every pass cannot hold a dead row up past the hour. **A carried row cannot be pressed**: the client gates the press on `facts.claimable` (`app/src/lib/owed.ts:107`, `owedPress.ts:167` answers `pending`, `:312` skips it) and renders "not claimable yet" (`OwedList.tsx:224`); a shed row carries no `claimReason`, so the copy is the generic one (NOTE N8). The answer's top-level `refresh: "shed"` (`mark_shed_rows_refresh`) makes the client re-read at the named interval (`owed.ts:120`, `:202`). The pin `fix837_d` (`owed.rs:14326`) holds the carry's shape, the second cut, the keep window and the collected exclusion.

**What the carry does not do**, stated: it does not make the refund PRESSABLE for an identity cut on every pass; it shows the row with `claimable: false` for an hour from its first judgement and then drops it again. The lane's answer to "every pass cut" is the tier's measurement that a 300-result identity is not cut at all (section 7, unverified by this lens), with the carry as the belt for a slow D1 (the #838 class). The carry runs after the `OWED_MAX_ROWS` truncation, LOW-4.

## 5. Findings

### MEDIUM-1. The shared write reads one row per JOIN input with no bound, on a scheduled pass whose candidates a stranger can shape

`record_join_hop_spends` loops `for input in &join.inputs` (`lowfund_topic_manager.rs:166`) and reads `get_spent_status(source, vout)` for every input before it knows whether the row is a hop (`:172`); nothing bounds the count. The discovery pass calls it for every POT candidate (`proof_fetcher.rs:2048`), and the candidates are every `pot_records` row with `spent = 0` older than an hour, examine-backoff aside (`d1_discovery.rs:1699`), with no shape check beyond "not a hop row". `tm_pot` admits any Poc5 covenant output; the door's `DoorBudget` breach on the gated arm is "the network judges", never a refusal, and Arcade accepts a valid transaction. So a stranger's covenant-shaped transaction with hundreds of P2PKH inputs (its own coins; the fee at 100 sat/KB is the cost) is a candidate every hour for as long as it stays unspent, and each pass issues N statements for it against the invocation's statement budget, the budget this repo already sizes passes against (the retire pass's 480, D17's "the D1 per-invocation query limit the 256 is sized against is unverified"). The examine stamp lands first (`note_spend_discovery_attempt`, `proof_fetcher.rs:2032`), so the pass dies at most once per backoff period, and the rest of that tick's discovery is lost each time. The same loop runs inside the readmission and both `/admin/readmit` arms on the request path. An honest JOIN has two inputs. **Fold:** bound the inputs examined (a `JOIN_INPUTS_MAX` of 16 is an order of magnitude over the honest two), prefer the inputs `join_hop_inputs` names and read the row only for those and for uncarried sources, count a truncation (`skipped = Some("inputs truncated")` beside `faults`), and pin it with a 64-input body that marks the first 16 and counts the rest.

### LOW-1. The belt parses the stored body with no limits

`join_spends_outpoint` (`owed.rs:1174`) calls `bsv_rs::transaction::Beef::from_binary(beef)` alone, where every other production read of stored bytes in the app layer goes through `beef_limits::parse_beef(.., APP_BEEF_LIMITS)` (`results.rs:285`, `logic.rs:573`, `credit_beef.rs:118`, `beef_guard.rs:238`, `owed.rs:2226`) or the canonical reader `load_stored_beef` (`routes.rs:429`), whose guard answers `OverLimit` and `Refuted`. The bytes are the index's own and passed the door under the engine's limits once, so the exposure is a hydrated parse of a body up to the engine's maximum, four pots a pass (`OWED_JOIN_POT_READS_PER_RECOMPUTE`); the lane's "no trust gate" note is right for `Refuted` (the JOIN's input list is the same under a refuted proof) and wrong for `OverLimit`. **Fold:** `beef_limits::parse_beef(beef, &APP_BEEF_LIMITS)` in `join_spends_outpoint`; a refused body is no word.

### LOW-2. The belt's window is the newest eight, with no rotation

`routes.rs:4606` to `:4610` sorts the index-unspent hops by `marker_created_at` descending and takes `OWED_JOIN_SEAT_HOPS_PER_RECOMPUTE` (8); the same eight every pass. The probe phase rotates its front slots by the recompute's minute for exactly this reason (`hops_view::order_probe_targets`, `hops_view.rs:1126`, the delta-verify's NEW-2). An identity with more than eight index-unspent hops (the fleet wallets: #793's loop-43 comment counts 26 'no press' rows in one pass) never asks the ninth. For such a hop whose pot the index holds but whose spend it never recorded, whose pot has since been SPENT (so the discovery pass never revisits it, N2) and whose chain rung is silent (the cut pass's `probes 0`), the `index-unspent` arm offers the sweep, Arcade refuses it, the sweep's eviction puts the hop in `evicted_hop_outpoints`, and the next pass offers it again with `JOIN_REFUSED_REASON`: #793's loop-43 shape, each press a refused broadcast. **Fold:** rotate the window by the recompute's minute as `order_probe_targets` does (the newest hop keeps the first slot), and skip a hop whose chain rung already names a spender; state the bound in the CLAUDE.md section beside the "at most 8 hops" sentence.

### LOW-3. The write's statement carries no pointer guard

`record_join_hop_spends` decides on a read (`:186`, `row.spent || row.spending_txid.is_some()`) and writes with the trait's `mark_spent`, whose unconfirmed branch is `UPDATE ... WHERE txid = ? AND outputIndex = ? AND spentConfirmed = 0` (`d1_discovery.rs:2097` to `:2103`): last-writer-wins among unconfirmed claims, the trait's stated rule. A pointer another writer lands between the read and the write (the conflict pass's competitor through `record_conflict_spender`, `admit_fast.rs:407`; a sweep's own door admission) is overwritten by the JOIN's. A confirmed write always wins and the #186 chaser confirms the competitor, so it self-heals; the readmission's own re-mark carries the guard in its statement (`remark_pot_spend_sql`, `admit_fast.rs:357`, `AND spendingTxid IS NULL`). **Fold:** a guarded write for this writer (a `mark_spent_if_unpointed` on the trait, or the D1 wrapper running `remark_pot_spend_sql`'s shape), and the Memory store's twin.

### LOW-4. The carry runs after the row cap, so the write plan's stated bound no longer holds

`rows.truncate(OWED_MAX_ROWS)` runs at `routes.rs:5439`; the carry at `:5492` then pushes up to 501 previous rows (`OWED_ROWS_READ_SQL`'s `LIMIT 501`) whose outpoints the pass did not derive; `owed_write_plan` (`:5509`, "at most 503 statements" in the step 8 comment) writes rows + 3 statements. Realistically the overlap is near total (one identity's games), but the bound is now by argument, not by construction, and the read handler truncates the served list to 500 (`routes.rs:7113`) so a carried row can be the one dropped. **Fold:** cap the carried count at `OWED_MAX_ROWS.saturating_sub(rows.len())` inside `carry_shed_rows`, or run the truncation after the carry and keep `walk_cut` true when it bites.

### LOW-5. The two new hot statements are not in the plan pin

`tests/d1_fleet_plans.rs` lists the hot statements by hand and neither `JOIN_SEAT_POTS_SQL` nor `JOIN_POT_BEEF_SQL` is in it (grep count 0). I ran both plans against the tables' schema with the three indexes: `SEARCH hp USING INDEX idx_hopparty_hop`, `SEARCH s USING INDEX idx_pot_hop_seats_marker`, `SEARCH pot USING COVERING INDEX sqlite_autoindex_pot_records_1`, and `SEARCH pot_beefs USING INDEX sqlite_autoindex_pot_beefs_1`: no scan, and `idx_hopparty_hop` exists (`d1/mod.rs:1337`). The working convention makes every hot statement a plan-pin row and every change to them a money change. **Fold:** add both statements to the pin's list.
