# FIX-936-LENS: the lens on overlay PR 188 (bsv-low #936)

Lane FIX-936-LENS, 2026-10-27 (stamps `date -u`: 19:51:11Z to 19:56:49Z for the runs). A cold review of PR 188
(`lane/READ-936` at `8cf04f54`, base main `eaaee0ec`) and its read `docs/audit/READ-936-2026-10-27.md`. Every line
reference below is at `8cf04f54`. No product code changed; no workerd, no `wrangler dev`, no tier was run.

## Verdict: NOT SOUND

The core move is right and should land: the gated engine write is created inside the future handed to
`ctx.wait_until` (`routes.rs:2030-2055`) and is first polled there, so a client cancel no longer owns the write's
statements. That is what the READ's own evidence supports (the invocation's `wait_until` work logged after the
`canceled` end: the pending watch's SEEN at 16:10:53.104Z, past 16:10:46.233Z + 6,732 ms).

What is not sound is how the PR learns that the request is gone. Everything the fix adds for that case (the cover
job, the after-write under `RequestGone`, the `request-gone` log line, `submit_write_outlived_request_total`) runs
only when the request's Rust future is DROPPED (`owned_write.rs:52-60`, `Handle::drop` sets `gone`). On the
platform a cancel never drops it: the `#[event(fetch)]` export is a wasm-bindgen async export
(worker-macros 0.8.7 `async_export.rs`), driven by `js_sys::futures::future_to_promise` -> `spawn_local`
(js-sys 0.3.106, the workers lock's, `src/futures/mod.rs:343-366`, `task/singlethread.rs`), whose task is dropped
only when its future completes. A cancelled request is a task that is never polled again, or one the task's own
wake resumes. Either way `gone` stays false, so on a cancelled request the PR runs the write whole and then runs
none of what follows it. The native pins prove the combinator under a `drop(request)` (`owned_write.rs` tests,
`fix936_c` and `fix936_d`) that the platform does not perform.

## Findings

### HIGH-1: a cancelled request's write lands whole with no write-side guard (#513), no S2, no cover

File: `crates/overlay-cloudflare/src/owned_write.rs:52-60` (the only setter of `gone`), `:128-143` (the hand-over
wait and the orphan call), `routes.rs:2030-2055` (cover and orphan wired to `gone`).

Failing input. A JOIN whose two seats submit through the gated arm (the arm cells' shape), the client closing both
connections after `admitted PENDING` while the write runs under the fleet's D1 queue (loop 44: up to 42 s), and an
Arcade refusal callback (a double spend) opening the eviction during the write (loop 18's pair 11 shape). The
eviction writes its OPEN marker and moves the rows that exist; the owned write then inserts `outputs`,
`transactions`, `pot_records`, `pot_beefs` after the move. What should re-evict them is the write-side guard
(`finish_past_deadline`'s `open_eviction` at `routes.rs:833`, or the request's own at `routes.rs:2131` on). Neither
runs:

- s1, the request never polled again: the task finishes the write, hands the output over and waits for
  `taken || gone` for ever (`owned_write.rs:128-136`); `orphan` (`finish_past_deadline`, `RequestGone`) never runs.
- s2, the request resumed by the task's wake (a pure Rust wake, no I/O): it takes the output (`taken = true`), the
  task ends with no orphan, and the request's own after-write (guard, S2) issues its D1 statements from the
  cancelled request, which is exactly the continuation the READ found does not run after a cancel.

The lens probe (`/Volumes/Lanes/out/wt-overlay-fix-936-lens/lens936_probe.diff`, a test added to a scratch copy of
`owned_write.rs`, not committed) drives both: the log is `["insert_output", "output_admitted_by_topic"]` for each,
no `cover`, no `orphan`, and in s1 the task stays Pending through 100 polls.

So an evicted JOIN can stand as held through the background write (judgement item 3: fails). The same loss drops
S2 (`routes.rs:887-893`: a report that is not durable is never enqueued), so a write a D1 fault left undone has no
replay and no job: the S4 symptom again (admitted PENDING, no pot row, no eviction). And the platform's own cut of
the task (30 s after the cancel) has no cover job, because the cover starts only on `gone` (judgement item 2: the
cover the READ names in section 4 does not exist on the platform).

Fold: the owned task must run the after-write itself, unconditionally (the guard is idempotent and S2's replay is
dedup-safe, so the request's answer path may keep its copy or read the task's), and the cover must not hang on a
Rust `Drop`: either put the deferred job at rest before the write starts (the #838 job's cost on every gated write)
or start it from the request's `AbortSignal` (`Request.signal`, behind the `enable_request_signal` compatibility
flag; the configs run `compatibility_date = "2024-12-01"`, `wrangler.low.toml:16`), never from the handle's drop.

### MEDIUM-1: the pins drive a cancel the platform does not make

File: `owned_write.rs` tests `fix936_c` (`drop(request)` after one poll) and `fix936_d`; `fix936.rs:26-68`.

`fix936_c` is offered as "the class, as eaaee0ec ran it", but a dropped Rust future is not what a cancel is on
wasm32 (above); the eaaee0ec cut is consistent with a request that is never polled again, which `fix936_c` would
also show, and which the fixed code does not survive (HIGH-1). `fix936_a` and `fix936_b` are source pins: they show
the wiring exists, not that it fires. Fold: a pin over the never-dropped request (the lens probe's two shapes) that
asserts the guard, S2 and the counter run, RED on `8cf04f54`; and the workerd cell below.

### MEDIUM-2: L53's check reads a line the fix never prints

File: `READ-936-2026-10-27.md` section 5; `routes.rs:790` (the counter), `:795` (the `request-gone` word).

Section 5 asks that every `canceled` gated `/submit` carry a `request-gone write landed after the answer` line and a
count in `submit_write_outlived_request_total`. Under HIGH-1 neither is ever produced on the platform, so L53 would
read red with the write landed, or a lane would read the counter's 0 as "no cancels". Fold: the measure must follow
the fold's detection (the task's own after-write logs and counts whether or not the request is waiting).

### LOW-1: a task that waits for ever holds the invocation to the `wait_until` cap

File: `owned_write.rs:128-136`. In s1 the task never resolves, so the invocation lives to the platform's 30 s cap and
the sibling `wait_until` work still running then (the pending watch, the #413 push) is cancelled with it and logged
`waitUntil() tasks did not complete`. Gone with HIGH-1's fold (no hand-over wait).

### LOW-2: the `RequestGone` after-write still says `past-deadline`

File: `routes.rs:785`, `:814`, `:864`, `:887`, `:907`. Only the landed line (`:795`) takes `cause.word()`; the
error, guard and S2 lines name `past-deadline` for both causes, and `:814` promises "the deferred job's run" where
under `RequestGone` the job exists only if the cover ran. Fold: one word per cause on every line.

### LOW-3 (pre-existing, stated): #838's past-deadline cover is still awaited in the request

File: `routes.rs:2076`. A cancel while `defer_past_deadline` puts the job at rest cuts that put; the write itself is
safe (its `finish_past_deadline` holds the handle in its own `wait_until`, `routes.rs:2065`). Not widened by PR 188.

## What holds (checked)

- The write's first statement runs in the owned task: `write` is boxed and not polled before `owned_write` takes it
  (`routes.rs:2016-2017`, `:2030`), and `ctx.wait_until(task)` precedes the race (`:2055`, `:2058`).
- The combinator: `cover` starts at most once (`owned_write.rs:98-107`), `orphan` runs only with an untaken output,
  a waiting request takes it (`fix936_e`).
- #838's past-deadline path is unchanged in behaviour: `Past(handle)` hands the handle to `finish_past_deadline`
  under `PastDeadline` in its own `wait_until`.
- Two seats' writes of one subject: two concurrent full submits of one body, as on eaaee0ec whenever neither request
  was cancelled (not new). The statements they share are idempotent: `INSERT OR IGNORE INTO outputs`
  (`d1_storage.rs:327`), `pot_records`' upsert (`d1_discovery.rs:2516`), `INSERT OR REPLACE INTO pot_beefs`
  (`:1606`); one applied row (#559 N4, not executed concurrently natively).
- The deferred job (when it exists) is #838's job, the same delay (`PAST_DEADLINE_JOB_DELAY_SECS` 45,
  `ef_deferred.rs:131`) and the same bytes at rest; it is not a dead letter and adds nothing to #576's bounds. A
  stranger buys one only by passing the broadcast gate (a fee), as #838's.
- No served word changes: the 200, 202 and error bodies are as on eaaee0ec; the new counter is additive.
- The engine's premise (`record_spent_coin_applied`, `engine.rs:2071`: a held coin means its transaction landed) is
  left unnarrowed, as the READ states. With the fold it still holds only if the task is not cut: a successor that
  removes the coin before the 45 s job runs makes a platform-cut half write permanent. For a JOIN the successors are
  the refund (behind its nLockTime), the settle and a hop sweep, all minutes later; stated, not pinned.

## What a fold must change (one line each)

1. Run `finish_past_deadline`'s after-write (walk count, landed guard, write-side guard, S2, notes) in the owned task on every gated write, not on `gone`.
2. Start the cover from the request's `AbortSignal` or before the write, never from `Handle::drop`.
3. Remove the hand-over wait in `owned_write` (no task may wait on the request).
4. Pin the never-dropped request (s1 and s2) and make it RED on `8cf04f54`.
5. Name the cause on every after-write log line (LOW-2) and move L53's measure to the task's own line and counter.
