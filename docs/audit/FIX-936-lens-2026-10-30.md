# FIX-936 lens (from scratch), 2026-10-30

**Target:** PR 236 (`lane/FIX-936`, `5eb071da` on main `1ab40c95`) —
"an admitted, SEEN-latched pot never leaves the index without its eviction
record". bsv-low #936, loop 52's S4 (beta, 2026-10-27).

**Verdict: SOUND.** No HIGH, no MEDIUM. 3 LOW, 4 NOTE.

The core money property holds: the heal can NEVER record a pot the engine did
not admit, and it classifies the healed pot exactly as a whole admission +
spend would. The fix is a strict improvement over the bug it closes (every
residual below is a proper subset of the pre-fix state, in which *every*
cut pot was permanently invisible). The LOW/NOTE items are residuals — some
stated in the lane's CLAUDE.md note, some with a money-adjacent consequence
the note does not spell — each with the fold it asks for.

---

## What the fix is, and what I verified

The engine notifies `ls_pot.output_spent(txid, output_index, topic, spender)`
only for a coin the topic **holds** (`engine.rs:1811` loops over
`v.previous_outputs`, the stored `Output` rows for the coins this spender
consumes; `output_spent` is the only production call site — `engine.rs:1873`,
every other `.output_spent(` in the tree is a test). So a spent `tm_pot` /
`tm_lowfund` outpoint with no `pot_records` row is an output the topic
admitted whose admission hook never ran (the write cut between
`Engine::submit`'s `insert_output` and `ls_pot`'s `store_record`). The fix
(`lookup_service.rs:391-404`, `:738-806`): in `output_spent`, when the
record read **answers absent** (not when it faults), record the pot FIRST from
the spender's carried source bytes, through the admission hook itself, then
write the spend pointer.

The four load-bearing checks, all verified in the tree:

1. **`output_spent` fires only for held coins.** `engine.rs:1811-1878`:
   the notification loop is over `previous_outputs`. A coin is in
   `previous_outputs` only because `find_output` returned it for this topic,
   i.e. the topic holds it. `tm_pot` admits only covenant outputs
   (`is_pot_covenant_script`), so a held `tm_pot` coin is a genuine covenant
   output. (`ls_pot.output_spent` additionally early-returns for any topic
   that is not `tm_pot`/`tm_lowfund`, `lookup_service.rs:342`.)

2. **The carried source is hash-bound to the held coin.**
   `record_held_output_from_spender` (`:745-756`) finds the spender input that
   spends exactly `txid:output_index`, takes its `source_transaction`, and
   **rejects it unless `source.id() == txid`** (`:762`). Since
   `txid:output_index` is a real admitted coin and `source.id() == txid` is a
   SHA256d binding, the carried source is byte-identical to the transaction
   the engine admitted. A forged/foreign carried source cannot pass: to reach
   the hook at all the attacker must first get the engine to *hold*
   `txid:output_index` under `tm_pot`, which requires a real covenant output.

3. **The heal reuses the admission hook's own shape gate.** It builds the
   pot's atomic BEEF from `source.to_beef(true)` and calls
   `self.output_admitted_by_topic(WholeTx{..})` (`:775-784`), which re-parses,
   re-checks `is_pot_covenant_script` (tm_pot) / `is_p2pkh_script`
   (tm_lowfund) and decodes the committed params from the output's own lock
   (`lookup_service.rs:227-307`). A P2PKH carried source under `tm_pot`
   records nothing (pin `fix936_c` case 3). The healed record's params,
   `pot_sats` and the `stake_a+stake_b == pot_sats` conservation check are
   the real pot's, so the verdict/signers written by the following
   `mark_spent` are identical to a normal admission + spend.

4. **The read-fault guard protects the verified-proof latch.** The heal runs
   only on `None` with `record_read_faulted == false` (`:397-404`). The
   rationale is real: `store_beef`'s admit write is `INSERT OR REPLACE … 
   proof_verified … 0` (`d1_discovery.rs:1605-1608`), so re-writing an
   already-recorded pot's beef would reset its verified-proof latch. Guarding
   on *answered-absent* means the heal only ever writes a pot with no latch to
   lose. `mark_spent` is `UPDATE … WHERE txid=? AND outputIndex=?`
   (`d1_discovery.rs:2068-2105`) — a true no-op on an absent row, so the
   fault branch's pointer write is genuinely the no-op the note claims, not a
   bare-pointer row. `store_record`'s `ON CONFLICT DO UPDATE` only COALESCE-
   fills absent decoded columns and never touches spend state
   (`d1_discovery.rs:2515-2534`); `MemoryPotStorage` mirrors both faithfully
   (`storage.rs:1692-1735` insert-if-absent/COALESCE, `:1738-1754`
   "absent outpoint is a no-op"), so the memory-store pins are a faithful
   proxy for these D1 semantics.

The engine is unchanged (the diff touches only `lookup_service.rs`,
`storage.rs`, the `d1_discovery.rs` log line, and `CLAUDE.md`). STEAK, the
submit gate's refusals and the admission answers are untouched. The heal's
`store_record`/`mark_spent` fire the existing `owed_dirty` triggers, so a
healed pot's refund flows into the owed list through the normal derivation.

**Pins (surface 5).** `fix936_a`/`fix936_b` drive a REAL engine
(`EngineBuilder` + real `PotTopicManager` + real `PotLookupService` wrapped in
`CutOnce`, which only hangs the first admission hook and delegates
everything else, incl. `output_spent`, to the real service). The heal runs in
the real `output_spent`, and the terminal `.expect("… is recorded")`
asserts the record is *present* — so the pin is not vacuous (a dropped source
would take the `Ok(None)` branch and fail the `expect`). This satisfies the
loop-17 lesson for the engine→`ls_pot` driver. `fix936_c` unit-tests the hook
over `MemoryPotStorage`. The pin fixtures carry the pot as the spender's
`source_transaction` and the engine's `subject_named_beef`
(`engine.rs:1653`, `to_binary_atomic` "never prunes") preserves it, so the
real parse repopulates it. **Gap:** see NOTE-2 — no real-SQLite/D1 harness
covers the heal (the `overlay-cloudflare` `fix936_*` pins are PR 188's
`wait_until` fix, step 1, not this heal).

## LOW

### LOW-1 — the read-fault branch proceeds without a replay, so a genuine half-write can be silently dropped
`lookup_service.rs:397-404`, `output_spent`.

On a record-read **fault** the heal is skipped and `output_spent` returns
`Ok` (no error, no `?`). The engine then treats the spend as applied: the
stale coin is deleted and nothing is replayed. If the pot was *genuinely*
half-written (cut, held coin, no record) and this is its only spend, the heal
is missed permanently — the coin is now gone, so there is no later spend to
retry on. This is the strict asymmetry with the heal-*write* fault
(`:401` `?`), which DOES propagate → the engine holds-unapplied → replay.

Failure scenario: a cut pot's refund arrives; `get_spent_status` suffers a
transient D1 read fault while `mark_spent` and `store_beef` succeed in the
same call → the pot is never recorded, never spent-in-index, never retried.
Narrow (read faults but writes don't, in one call), and still a strict subset
of the pre-fix bug. The note states "a read that faulted records nothing" but
frames only the optimistic case ("the pot may well be recorded"); it does not
state that a genuinely-unrecorded pot is then lost with no replay.

**Fold:** on the read-fault branch, prefer to propagate (fail the spend so
the engine keeps the coin and replays) rather than proceed — or, if fail-open
on transient faults is intentional, say so and state the dropped-half-write
consequence in the note. (Propagating costs more replays on transient faults
for already-recorded pots; that trade-off is the decision to record.)

### LOW-2 — a cut pot spent by a spender that does not carry its bytes is not healed, and the pointer is a silent no-op
`lookup_service.rs:745-767`; `mark_spent` `d1_discovery.rs:2068`.

If the spender carries no `source_transaction` for the pot (a PROVEN refund
submitted after the pot's block, or any txid-only ancestry), the heal returns
`Ok(None)`; `admitted` stays `None`; `mark_spent` over the absent record is a
no-op; only `store_beef(spending_txid)` lands (the spender's bytes, under the
spender's txid). So the pot and its *completed* spend stay invisible to the
index: no `pot_records` row, so the owed judge / history / `/beef/:pot` never
see them. The note states "an absent source leaves the hook as it was" but
does not spell this owed/history consequence.

Not a money loss (the refund is on-chain; a player is never *blocked* — their
0-conf refund carries the pot and heals on submit; and this is a strict subset
of the pre-fix invisibility). But LOW's late/proven refund path, if it exists,
lands here.

**Fold:** state the consequence in the note, and — if a proven/txid-only
spend of a cut pot is reachable on LOW — consider sourcing the pot's bytes
from the engine's own `transactions`/stored copy (keyed by `txid`) when the
spender does not carry them, before falling back to `Ok(None)`.

### LOW-3 — a heal whose `store_record` lands but `store_beef` faults leaves a `pot_records` row with no `pot_beefs`, and is never completed
`lookup_service.rs:775-784` → `output_admitted_by_topic`
`lookup_service.rs:309-319` (record first, beef second).

If the heal's `store_record` lands but its `store_beef` faults, the heal
returns `Err` → spend held-unapplied → replay. On replay `get_spent_status`
answers `Some` (the record landed) → the heal is **skipped** → `mark_spent`
marks it spent and `store_beef(spender)` runs, but the pot's OWN
`pot_beefs` row is never written. Unlike the normal admission path (which
re-runs both `store_record` and `store_beef` on every replay because it does
not consult `get_spent_status`), the heal's `get_spent_status` guard makes
this partial state terminal. The note states "a pot recorded without its
bytes … is not healed" — this is that residual — but not that `/beef/:pot`
and any pot-proof read are then permanently empty for a pot the owed judge
still serves from `pot_records`. Display/proof only, not money.

**Fold:** when the record is present but `get_beef(txid)` is absent, re-write
the pot's bytes (one extra read on the heal path), closing the record-without-
beef window the heal itself opens.

## NOTE

### NOTE-1 — an UNSPENT cut pot has no automated reconciler; it is invisible until its spend arrives
The heal fires only at a spend. A cut pot that is never spent stays held by
the engine as a live UTXO with no `pot_records`/`pot_beefs` row; the retire,
conflict and reorg passes all read `pot_beefs`/live pots, so none can see it.
The note names only the manual L53/L54 D1 query ("a `pot_records` row for
every `tm_pot` applied txid of a covenant transaction") as the evidence — a
detection query, not a heal. The money is on-chain and the pot heals the
moment its refund/settle is registered (the common case), so this is a
visibility residual, not a loss. Worth stating that nothing reconciles an
engine-held-but-unrecorded coin automatically.

### NOTE-2 — the heal is unpinned over the D1 backend
The heal's only pins (`fix936_a/b/c`) run over `MemoryStorage` /
`MemoryPotStorage`. No real-SQLite / `d1_discovery` harness exercises the heal
path's actual SQL (`store_record_sql`'s `ON CONFLICT`, the admit `store_beef`
forcing `proof_verified=0`, `mark_spent_sql`'s no-op-on-absent) or the new
`D1PotStorage::note_recorded_at_spend` line. The `overlay-cloudflare`
`fix936_*` pins are PR 188's `wait_until`-ownership fix (step 1), not this
heal. I verified by reading that `MemoryPotStorage` mirrors the three relevant
D1 semantics and that the guard prevents reaching the `proof_verified`-reset,
so the risk is low — but the D1 SQL on the heal path is asserted only by
inspection, not by a harness.

**Fold:** add one real-SQLite leg over `D1PotStorage` that records a held pot
at its spend and asserts the `pot_records`/`pot_beefs` rows and the untouched-
on-recorded guard (the `ON CONFLICT`/`proof_verified` behaviour the memory
store only approximates).

### NOTE-3 — the heal records a cut pot at the FIRST spend seen, which may be a competing unconfirmed double-spend
Because the heal fires in `output_spent`, a cut pot is recorded (correctly —
it is the real pot) and marked spent by whatever spender the engine processes
first, which on the public `historical-tx-no-spv` path could be an attacker's
unconfirmed double-spend naming the pot as input. This is not a regression:
`mark_spent`'s confirmed-CAS (`d1_discovery.rs:2089-2102`, pinned by the
existing `confirmed_pointer_survives_later_unconfirmed_claim` test) lets the
real confirmed spend win, and a later unconfirmed real refund re-marks it
(last-unconfirmed-writer). Pre-fix the cut pot was simply invisible; post-fix
it is tracked and the pointer self-corrects. Noted for completeness: the heal
inherits — does not widen — the existing unconfirmed-spender pointer surface.

### NOTE-4 — the heal writes directly to `ls_pot` storage, outside the worker's eviction-ledger / landing guard
The heal records `pot_records`/`pot_beefs` through `output_admitted_by_topic`
without consulting the worker's eviction ledger or landing guard
(`admit_fast`). This is correct under the held-coin invariant: a COMPLETE
eviction shadow-moves the coin, so an evicted pot's coin is not in
`previous_outputs` and `output_spent` never fires for it. The only way to
record under an open eviction is a fault-orphaned eviction (ledger row written,
shadow move not) whose coin is still held and is then spent — an extreme
corner. Noted so the reviewer knows the heal is a write below the worker's
guard pipeline, sound by the invariant.

## Answers to the five money surfaces

1. **The new write shape gate / txid / bytes:** SOUND. Shape gate is the
   admission hook's own; txid is hash-bound (`source.id() == txid`); the bytes
   are the carried source the spender's (engine-processed) BEEF carries; a
   forge requires the engine to already hold the coin under `tm_pot`, which
   requires a real covenant output.
2. **Read-fault guard:** A faulted read records nothing AND the pointer is a
   genuine no-op over the absent record (not a bare-pointer row) — so not the
   pre-fix hole. But the fault branch does not replay (LOW-1).
3. **Heal reach (spender never arrives):** The unspent-never-spent cut pot is
   the residual; it is invisible until spent and only the manual L53/L54 query
   names it (NOTE-1). A spender that does not carry the bytes also leaves it
   unhealed with a silent no-op pointer (LOW-2).
4. **Anything else move:** No. Admission answers, STEAK, gate refusals, the
   eviction ledger's OPEN-marker rule and the write-side guard are untouched;
   the heal is additive and integrates with the owed-dirty triggers. (NOTE-4
   records that it writes below the worker guard, sound by the invariant.)
5. **The pins:** `fix936_a/b` exercise the real engine→`ls_pot` production
   driver (not a port fake) and are non-vacuous; `fix936_c` unit-tests the
   hook. The D1 backend of the heal is unpinned (NOTE-2).
