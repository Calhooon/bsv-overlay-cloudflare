# Releasing the overlay crates

1. Every change reaches protected `main` through a PR, with linear history and admins included.
2. Rebase-merge only with `test`, `fmt`, `clippy`, and `wasm32` green; the captain also runs the full `make ci` on the merge commit.
3. Integrate the callable L2-gate `ci.yml` before releasing 0.1.0; its baseline is `engine-e592-2026-10-10` plus #74's build object.
4. A release PR updates both workspace versions, compatible internal dependency versions and `CHANGELOG.md`; all five packages share the version. Rust 1.88 is the measured minimum (`rust-version`, checked by the gate's `msrv` job on every target); the other jobs build at 1.95.0.
5. Bootstrap the five new crates once from the captain's machine, in order: `bsv-overlay-engine`, `bsv-overlay-discovery`, `bsv-low-proof-replay`, `bsv-worker-build-info`, `bsv-overlay-cloudflare`; use `workers/Cargo.toml` for the latter three and wait for each registry index entry.
6. After each bootstrap publish, create its crates.io trusted publisher for owner `Calhooon`, repository `bsv-overlay-cloudflare`, workflow `release.yml`, no environment; hold the release workflow for the bootstrap `v0.1.0` tag push, then restore it so the version is not published twice.
7. Subsequent releases tag the merged commit `vX.Y.Z`; `.github/workflows/release.yml` checks the tag's form, workspace versions and the tag's line (a stable tag on `main`, a prerelease tag `vX.Y.Z-beta.N` on `beta`: item 14), calls the four CI jobs, dry-runs and publishes in dependency order, waiting for each index entry.
8. Subsequent publication uses OIDC trusted publishing only, with no stored repository token. Each crate job obtains its own short-lived token. Without its trusted publisher, authentication fails closed.
9. Publication intentionally omits `--locked` even though both workspace locks are committed: packaged path dependencies resolve from the registry; gates test the checkout locks and package verification tests the registry resolution.
10. Multi-crate publication is not atomic: after a partial release, preserve published versions. Rerun a failed job only if its crate version is still unpublished; if upload succeeded but indexing timed out, do not rerun that publish. Code fixes or recovery that would republish require a new release PR and version; yank a bad published version when appropriate.

## The two lines and the direction rule

Items 1 to 10 describe one line, `main`. The repository takes a second, `beta`, cut from `main`'s tip by the owner's word. Until that branch exists on the remote nothing above changes and the `beta-born` check passes, saying so. Whether the line exists is one tracked line, `.github/lines`: `beta unborn` today, `beta born` from the birth (item 22). From the day it exists:

11. Every change is born on `beta`: a pull request into `beta`, gated as item 2 gates `main` (`ci.yml` runs on both lines).
12. `main` takes only a quick fix of a NAMED CLASS, each commit a `git cherry-pick -x` of a `beta` commit with its test. The classes:
    - a security advisory;
    - a panic, or a wasm trap, on input;
    - a wrong verdict: consensus, a BEEF, or a coin credited, offered or spent wrongly;
    - a break in a live dependent;
    - the front pages: `README.md`, `SECURITY.md`, release notes;
    - a toolchain mend: what a required check on `main` demands after CI's toolchain moved, with no behaviour change;
    - an additive item a dependent's stable line needs.

    A pull request into `main` says which class it is in, in one line of its description: `Class: <one of the seven>`. A change in none of them waits on `beta` for the cut.
13. Quick fixes travel in roll-ups: one stable patch release carries the fixes that are ready, so a dependent hops once per roll-up, not once per fix.
14. A prerelease is a tag `vX.Y.Z-beta.N` on `beta`'s tip, with both workspaces at `X.Y.Z-beta.N` by a pull request into `beta`. `release.yml` admits that form only on `beta`, a plain `vX.Y.Z` only on `main`, and no other form of tag. Nothing on `beta` is reverted and landed again so that a prerelease carries a pin alone: the prerelease is what `beta` is.
15. What `main` carries that `beta` does not goes to `beta` once, by `git cherry-pick -x`. After that nothing is ported from `main`, because nothing is born there. The one commit born on `main` is a stable release's own commit (item 4: versions and `CHANGELOG.md`); a commit of `beta` that names it by a `(cherry picked from commit <sha>)` line, and is not empty, carries what it says to `beta`.
16. `beta` merges into `main` once, at the cut, on the owner's tag. HOW it merges is the owner's ruling, not yet given. The two candidates, neither chosen here:
    - one rebase merge of `beta` into `main` (every commit of `beta` gets a second sha on `main`);
    - one merge commit, with linear history lifted for that one merge and `main` merged into `beta` by a pull request first (`beta` becomes an ancestor of `main`, no sha moves).
17. A finding of a read on `beta` stops a landing only when it is one of item 12's classes. Any other finding becomes a row for the line's own work. The deep reads are spent once, at the cut.

Two checks hold the rule, so that no memory has to. Both are `scripts/check-lines.py` (Python 3, standard library), called by jobs of `ci.yml` and tested by `scripts/tests/lines.sh` (`make lines`, part of `make ci` and of the hosted `lint` job):

18. `beta-born`, on every pull request into `main`: each commit of the pull request is on `origin/beta` by sha, by patch, or by a cherry-pick line in either direction (the commit names a commit of `beta`, or a commit of `beta` names it); or it is a release commit, which the check says in its output (it changes only the manifests, the two locks and `CHANGELOG.md`, every changed manifest or lock line a version). A commit that is none of these is refused by sha and subject, and so is a merge commit. The cut's own pull request needs no flag while its head is `beta`'s tip: every commit is on `beta` by sha, and none is left to judge. What each kind of evidence is worth:
    - The patch is compared VERBATIM (`git patch-id --verbatim` over each side). `git cherry` strips whitespace before it hashes, so the same lines at another indentation would be the same patch to it; here they are another patch, and Python, YAML and the Makefile mean something by their indentation.
    - The line is the one `git cherry-pick -x` writes, alone on a line of the message: `(cherry picked from commit <40 hex>)`. The same words inside a sentence are not the line. A line naming a commit `beta` does not hold passes nothing.
    - A commit that passes by a line (and not by sha or patch) is not empty and touches ONLY paths the named `beta` commit touches (or, for a line written from `beta`'s side, the paths of the `beta` commit that names it). So a line cannot carry an unrelated file onto `main`. LEFT OPEN, stated: inside those paths the content is not compared, because a pick resolved by hand differs from its source by definition. A reviewer reads a hand-resolved pick against the `beta` commit it names; the check says which paths, not which bytes.
19. `main-in-beta`, on every pull request into `beta` (judged on the pull request's merge commit) and every push to `beta`: each commit of `origin/main` is on the tree by sha, by verbatim patch, or by a cherry-pick line in either direction. It has no release-commit exception (item 15). A commit of the tree that names a commit of `main` carries it only when it is not empty: a link over no content carries nothing (and a rebase merge drops an empty commit). Its paths are not bounded by the named commit's: a release commit of `main` moves versions `beta` does not share. On a push it reports after the push, and on a pull request its green goes stale when `main` moves: it holds only where item 23's protection names it.
20. Both checks read patches and links, never ancestry. `main` keeps linear history and merges by rebase (item 1), so a fix has one sha on `beta` and another on `main`; the patch and the `-x` line survive the new sha. Whether the cut gives every commit of `beta` a second sha too is item 16's open ruling; the checks hold under either candidate. A pick resolved by hand has another patch, so it passes only by its `-x` line: add the line with `git commit --amend` when a pick was made without it.
21. A check that cannot run (a shallow clone, a remote that does not answer, a marker that says neither state) exits 2 and is never read as a pass. The hosted jobs run the script of the line being PROTECTED, never the pull request's own copy: `beta-born` runs the copy at the pull request's base, `main-in-beta` the copy at the pull request's base or at `beta` as it stood before a push. Where that commit holds no copy (the pull request that added the check; the push that creates `beta`) the tree's copy runs and the step says so in one line. So a pull request that edits `scripts/check-lines.py` is judged by the check it would replace. LEFT OPEN, stated: the job itself lives in `ci.yml`, and for a `pull_request` event GitHub runs the workflow file of the pull request's own merge commit ("Each workflow run will use the version of the workflow that is present in the associated commit SHA or Git ref of the event", and for `pull_request` that commit is the "Last merge commit on the `GITHUB_REF` branch", `refs/pull/PULL_REQUEST_NUMBER/merge`; docs.github.com/en/actions/concepts/workflows-and-actions/workflows and docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows, read 2026-11-27). A pull request from a branch of this repository that edits the job in `ci.yml` is therefore run by its own edit; no script can cure that. What holds it: a required check that never reports blocks the merge (so deleting the job does not pass), `CODEOWNERS` review of `.github/`, and a reviewer reading any change under `.github/workflows/`. The pages read do not say whether such a pull request needs an approval to run; none was observed here.
22. THE BIRTH, in this order, by the captain on the owner's word: (a) create `beta` at `main`'s tip; (b) protect it as item 23 says, before anything lands on it; (c) the first pull request into `beta` changes `.github/lines` from `beta unborn` to `beta born`; (d) that commit is picked to `main` with `-x` by a pull request (the birth's own step, by the owner's word that cuts the line, not one of item 12's classes; `beta-born` passes it by patch); (e) `main`'s protection adds `beta-born`. The marker is read at a pull request's BASE, so from (d) a pull request into `main` while the remote has no branch `beta` FAILS: deleting `beta` no longer makes every pull request into `main` pass. A cut never deletes and re-creates `beta`.
23. What the protections must name, or the checks gate nothing. `beta`: pull requests required (no direct push); `lint`, `checks` and `main-in-beta` required, strict (the branch current before merging); never deleted, never force-pushed; admins included. `main`: what item 1 has, plus `beta-born` required. Both are settings of the repository, changed by the captain, not by a pull request.
24. The update loop is born on `beta` too: `.github/dependabot.yml` names `target-branch: beta`, so the bot's pull requests target `beta` and never put a commit born on `main` there. Dependabot's documentation says of the option: "All pull requests for version updates are opened targeting the specified branch", and "security updates always use the default branch for the repository" (docs.github.com/en/code-security/dependabot/working-with-dependabot/dependabot-options-reference, read 2026-11-27); security updates are off for this repository, and if they are turned on, their pull requests into `main` are refused by `beta-born` and are landed on `beta` by hand. NOT established from the documentation: that the configuration is read from the default branch only (the pages read say it of the manifests, not of the file), and what a run does while `target-branch` names a branch that does not exist; so `beta` is created immediately after the change that names it lands. `dependabot-automerge.yml` still selects the base `main`: it is one of several byte-identical copies of a shared template and is not edited here alone. Until the template selects `beta`, a bot pull request into `beta` is not armed and merges by hand, and nothing of the bot reaches `main`.
